## 摘要

现代高性能计算（HPC）环境依赖**混合存储系统（hybrid storage system, HSS）**，即把多种在延迟、带宽、耐久度和容量上各异的存储设备组合起来，以满足数据密集型应用对性能、容量与成本的要求。HSS 的性能高度依赖两条关键的数据管理策略：(1) **数据放置**，即为每个到来的写/分配请求选择最合适的设备；(2) **数据迁移**，即跨设备重组已存放的数据（把热数据预取到快设备、把冷数据驱逐到慢设备）以维持高性能——后者会因数据错放与访问模式/HSS 状态变化而随时间退化。这两条策略**紧密耦合**，只优化其中一条而不考虑另一条，会得到次优的 HSS 性能。遗憾的是，已有工作只优化二者之一。

我们的目标是设计一种全流程（holistic）的数据管理技术，同时优化放置与迁移，以充分发挥 HSS 潜力。为此我们提出 **Harmonia**，一种基于多智能体强化学习（multi-agent RL）的数据管理技术。Harmonia 使用两个轻量、自治的 RL 智能体——**数据放置智能体**与**数据迁移智能体**——它们各自针对当前负载与 HSS 配置调整策略，并相互协调。

我们在真实 HSS 配置上评估 Harmonia，最多使用四种异构存储设备与 25 个数据密集型负载。在**性能优先**（**成本优先**）的双设备 HSS 上，Harmonia 平均优于表现最好的先前方案 **29.3%（44.8%）**；在三设备、四设备 HSS 上分别平均优于 **38.9%** 与 **39.2%**。这些性能收益的代价极低：推理延迟 **240 ns**，两个智能体合计仅占 **206 KiB DRAM**。

## 1 引言

现代应用（机器学习、数据库、图处理、基因组分析）处理大体量数据，产生不规则且快速演化的访问模式，对存储系统提出很高的性能、容量与成本要求。为满足这些要求，HPC 环境依赖 **HSS**：把多种在延迟/带宽/耐久度/容量上各异的设备（快速 SSD、小容量，慢速 HDD、大容量）集成在一起。

HSS 的性能取决于两条核心策略：**数据放置**与**数据迁移**。HSS 性能会因 (i) 数据错放、(ii) 工作负载访问模式与 HSS 状态变化而随时间退化。

为现代 HPC 设计有效的放置与迁移策略并不简单，有四个关键原因：

1. HPC 负载的访问模式变化很快（突发式检查点写入、多租户访问），并导致 HSS 状态频繁变化（设备容量利用率、读写延迟波动）；
2. 放置策略处在 **I/O 处理的关键路径**上，微秒级延迟波动会直接影响应用性能——因此放置决策必须准确且开销极低，即使在高并发下；
3. 时机不当的迁移会 (i) 干扰应用到来的 I/O 请求，(ii) 让频繁访问的数据滞留在慢设备上，(iii) 加剧快设备的争用或利用率不足，从而降低吞吐与尾延迟；
4. 放置与迁移在**共享的动态环境**中运作；缺乏协调时二者可能做出相互冲突的决策，损害性能与设备寿命。

**先前工作的局限。** 已有 HSS 数据管理工作只**孤立地**优化放置（如 [78, 79, 82, 86–124]）或迁移（如 [80, 84, 103, 106, 125–130]），在真实部署中导致次优性能。原因：一个优化的放置策略若迁移决策保持静态或对变化无感，就无法维持长期性能；而一个优化的迁移策略也无法弥补错放带来的不必要数据移动、带宽浪费与设备磨损。

我们的动机研究显示：即便最先进的数据放置技术 **Sibyl** [102]，在性能优先（成本优先）HSS 上的平均 I/O 请求延迟也比 **Oracle** 高出 **100.4%（176.2%）**——Oracle 表示"完美知晓未来 I/O 访问模式、做出最优放置与迁移决策"的理想策略（见 §3）。Sibyl 延迟更高的原因是它的**启发式迁移策略**：(1) 依赖有限的工作负载特征（如页访问频率），(2) 在 I/O 处理关键路径上迁移页。

**扩展后的数据管理技术。** 由于没有先前工作同时优化二者，我们构造了**四种扩展技术**（见 §3），把最先进的放置（如 Sibyl）与迁移（如 RNN-HSS）策略组合起来。§3.4 的评估显示：这些技术反而不如它们的组成技术——因为放置与迁移策略对彼此的动作无感，导致决策冲突、不必要的数据移动、带宽浪费、设备寿命下降与端到端性能降低。这些结果说明：要达到高 HSS 性能，必须**协同设计**放置与迁移。

**我们的目标**是设计一种全流程的 HSS 数据管理技术，以协调的方式同时优化放置与迁移。为此我们提出 **Harmonia**，一种多智能体在线 RL 技术，在实现二者协同的同时联合优化两条策略。

**核心思想。** Harmonia 采用两个轻量自治的 RL 智能体——数据放置智能体与数据迁移智能体——通过协作提升 HSS 性能。

- **放置智能体**为到来的页选择最合适的 HSS 设备。它建立在 Sibyl 之上，但引入了 (1) 新的、与迁移相关的状态特征，(2) 一种鼓励有效利用快设备的奖励结构（见 §4.2）。
- **迁移智能体**持续监控 HSS 中已放置的页，识别迁移候选及其目标设备；其奖励依据"迁移对未来 HSS 性能的影响"来分配。

两个智能体独立运作，但通过影响共享 HSS 环境的动作相互协调。这种解耦的多智能体设计让每个智能体专注于自己的任务，同时缓解单智能体 RL 形式化中固有的策略干扰（policy interference）。§3.4 显示：试图同时优化放置与迁移的单智能体，在性能优先（成本优先）HSS 上比最佳先前方案延迟高 **21.9%（30.5%）**，原因是任务干扰——优化迁移会干扰放置策略，因为它们是两项不同的任务（见 §3.2）。

**评估。** 我们在真实 Linux 系统上使用 25 个数据密集型负载与最多四设备的多种 HSS 配置评估 Harmonia。相比最佳先前方案 Sibyl：延迟在双设备 HSS 上改善 **29.3%（44.8%）**，在三/四设备 HSS 上改善 **38.9%（39.2%）**；推理延迟 **240 ns**，两智能体合计存储开销 **206 KiB**，使其适用于延迟敏感的 HPC 应用。

**主要贡献：**

- 表明先前的 HSS 数据管理方案并未同时优化放置与迁移，并在真实 Linux 系统、多种 HSS 配置上经验性地展示了它们的局限；
- 构造了四种"最先进放置 + 最先进迁移"的组合技术，并表明它们**不如其组成技术**；
- 提出 Harmonia：基于多智能体 RL 的轻量 HSS 数据管理技术，用两个 RL 智能体协同优化放置与迁移；
- 通过严格的真实系统评估，证明 Harmonia 在多种 HSS 配置与大量数据密集型负载上持续优于最先进的数据管理技术。

## 2 背景

### 2.1 混合存储系统

HSS 有两个关键组件：(1) 多种特性各异（I/O 延迟、带宽、容量）与协议各异（NVMe 或 SATA）的存储设备；(2) **HSS 管理层层**，负责在设备之间编排数据放置与数据迁移。典型 HSS 组合快速低容量设备（高端设备）与较慢高容量设备（中端、低端设备），以在性能、容量与成本效率之间取得平衡。

**HSS 管理层。** 通常实现在宿主 OS 内核空间，概念上类似 Linux `md` 子系统（在多设备上提供软件 RAID 0）。与 RAID 不同：RAID 用固定条带策略放置数据且不做运行时迁移，而 HSS 管理层**动态地**执行放置与迁移。

HSS 管理层执行三项关键功能：

1. (i) 向应用/文件系统暴露**统一的平坦虚拟地址空间**，使数据访问不暴露底层设备的异构性；(ii) 把虚拟地址映射到设备特定的逻辑块地址（LBA）；(iii) 把应用的读写操作翻译为 NVMe 或 SATA I/O 请求。
2. 执行两项性能关键任务：(1) 把到来的 I/O 请求数据**放置**到最合适的设备；(2) 跨设备**重组**已放置的数据以维持长期性能。
3. 为完成上述任务，在宿主 DRAM 中维护**元数据**：虚拟地址到设备 LBA 的映射、I/O 请求特征（请求类型、尺寸）、存储设备特征（容量与当前利用率）。

### 2.2 强化学习（RL）

RL 中智能体通过与环境的交互，为特定目标学习最优策略。RL 形式化（图 2）包含四个关键组件：

1. **状态**：环境在给定时刻的可观测信息。设 $S$ 为所有可能状态的集合，$s_t \in S$ 是时刻 $t$ 的状态。
2. **动作**：智能体观测 $s_t$ 后从动作集 $A$ 中执行 $a_t$，使环境转移到 $s_{t+1}$。
3. **奖励**：针对把状态从 $s_t$ 变为 $s_{t+1}$ 的 $a_t$，智能体收到数值奖励 $r_{t+1}$，量化所选动作的效用。
4. **策略**：$\pi$ 定义智能体在每个状态下如何选动作。RL 智能体要学习使累积奖励最大的最优策略 $\pi^*$，其确定依赖于最优动作价值函数 $Q^*$（Q 值）。$Q(s,a)$ 表示在状态 $s$ 采取动作 $a$ 得到的期望累积奖励。

**多智能体 RL（MARL）。** MARL 涉及多个相互交互、并与共享环境交互的 RL 智能体。先前工作表明：当多个任务的相似度低（输入、目标、动作不同）时，单个 RL 智能体难以同时有效优化它们——从一个任务学习会干扰另一个任务的学习，导致训练不稳定与次优策略。MARL 通过让每个智能体在自己的目标与时间尺度上专精，可有效处理多个不相似的任务。

## 3 动机

### 3.1 为什么 HSS 数据管理适合用 RL

四个关键原因：

1. RL 从系统级反馈**在线学习**，既不需要在标注数据上预训练，也不需要频繁重训，因此能持续适应 HSS 中常见的访问模式与系统状态变化；
2. RL 自然处理"每个动作都改变系统状态并影响长期行为"的复杂决策——通过优化累积回报，RL 学到的策略会考虑决策的**长期影响**，这对"放置与迁移影响设备利用率与整体性能"的 HSS 至关重要；
3. RL 对 HSS 典型的不规则访问模式依然有效，因为它隐式学习**基于价值**的策略（估计决策的性能影响），而不是直接预测未来的 I/O 请求。为展示现代数据密集型负载的不规则性，论文给出选定负载 `ssd-02` 在 300 秒执行期间访问的虚拟地址（图 3(a)）与 I/O 请求尺寸（图 3(b)）：(1) 应用访问范围极广（$1\times10^6$–$1\times10^9$）且**无重复出现的访问模式**；(2) 请求尺寸从随机访问（4 KiB）到大的顺序访问（128 KiB）变化。许多选定负载都有类似的动态变化。先前的启发式与监督学习方案在粗粒度间隔上做固定决策，无法有效适应这种动态变化（见 §3.4）。Sibyl 已表明 RL 在 HSS 数据放置上优于启发式与监督学习方案；
4. RL 能以极小的额外设计成本在多种系统配置间泛化，这对集成了多种异构设备的 HSS 配置很合适。

### 3.2 HSS 为什么需要多智能体 RL

尽管 RL 很适合 HSS 数据管理，**单个** RL 智能体并不理想，因为放置与迁移在三方面根本不同：

1. **作用对象不同**：放置决定新 I/O 请求数据写到哪；迁移重组已放置的数据。
2. **目标不同**：放置要在关键路径上最小化每请求 I/O 延迟并管理快设备利用率；迁移关注长期 HSS 性能。
3. **时间尺度不同**：放置处在 I/O 处理关键路径上；迁移相对于应用的 I/O 请求**异步**执行。

当单智能体试图联合优化二者时，这些差异会造成学习干扰（见 §2.2）。§3.4 显示单智能体形式化（SAPM）在同时处理放置与迁移时表现很差，从而支持多智能体形式化。

### 3.3 先前的 HSS 数据管理技术

已有技术通常只优化放置或迁移之一。论文评估的代表性技术：

**数据放置技术**（两类主流：启发式与 ML 式）：

- **CDE（Cold Data Eviction）** [86]：启发式。把热数据或随机（冷数据或顺序）数据放到快（慢）设备；用过去的访问频率判断热度、用请求尺寸判断随机性。快设备满时按 LRU 逐出。
- **Sibyl** [102]：RL。考虑 I/O 请求的多种特征（请求类型与尺寸）与 HSS 状态（设备容量、I/O 延迟）来做放置决策；快设备满时同样按 LRU 逐出。

**数据迁移技术**（强监督学习式，主动按预测的页访问频率重组数据）：

- **K-SVM** [106]：k-means 辅助的 SVM 分类器，基于过去访问频率识别迁移候选页与目标设备。
- **RNN-HSS** [103]：用 RNN 预测未来页访问频率，据此识别迁移候选与目标设备。

二者都在**固定间隔**（如每 1000 个到来请求）于 I/O 处理**关键路径上**执行迁移，并使用固定的启发式放置（例如 K-SVM 把数据全放快设备直到满）。

**扩展后的数据管理技术**（本文构造，用于检验"组合最先进放置 + 最先进迁移"是否能提升性能）：

- **Sibyl+K-SVM**、**Sibyl+RNN-HSS**：Sibyl 分别与两种 ML 迁移技术组合；
- **CDE+RL-Migr**：CDE 与一个 RL 迁移智能体组合，该智能体采用与 Harmonia 迁移智能体相同的设计（状态特征与奖励结构，见 §4.2）；
- **SAPM（Single Agent for Placement and Migration）**：用**单个** RL 智能体联合优化放置与迁移，对每个到来请求做放置，仅在系统空闲时迁移以避免干扰；状态特征与奖励结构与 Harmonia 相同，且超参经过仔细调优以求单智能体形式化的最佳表现。

论文明确指出：CDE+RL-Migr 与 SAPM 是本文为"造出更强技术"而新开发的技术。

### 3.4 先前技术的有效性

**方法。** 在真实系统上（表 3）以性能优先与成本优先两种 HSS 配置，对 20 个来自五个基准套件的数据密集型负载（表 4）评估 8 种先前数据管理技术。并与两个理想基线比较：

- **Fast-Only**：假设快设备大到可容纳整个负载的理想策略；
- **Oracle** [204]：在设备容量约束下、以对全负载未来 I/O 访问模式的**完整知识**做放置与迁移，使平均 I/O 请求延迟最小；Oracle 在空闲期迁移，不产生迁移引起的延迟开销。图中所有数值归一化到 Fast-Only。

**结果（图 4）**五个关键观察：

1. **所有先前技术在每种配置与负载下都落后于 Oracle。** 最好的先前方案 Sibyl 在性能优先（成本优先）HSS 上平均 I/O 延迟比 Oracle 高 **100.4%（176.2%）**。Sibyl 的 RL 放置能适应负载与系统变化，但它的**启发式迁移策略** (i) 无法适应负载与系统状态变化，(ii) 在 I/O 处理关键路径上驱逐页。
2. **Sibyl 优于 CDE、K-SVM、RNN-HSS**，分别高 **24.7%（9.7%）、22.4%（32.9%）、19.0%（11.4%）**，因为它的自适应 RL 放置更强；其余基线依赖启发式或监督学习，只用到有限的工作负载与 HSS 特征。
3. **Sibyl+K-SVM 与 Sibyl+RNN-HSS 反而比 Sibyl 更差**——朴素组合导致 (i) 放置与迁移决策冲突带来的不必要数据移动，(ii) Sibyl 策略收敛变慢。
4. **CDE+RL-Migr 平均比 Sibyl 差 7.1%（12.4%）**。在读密集负载（RocksDB、MLPerf）上它与 Sibyl 相当，因为其 RL 迁移智能体主动把频繁读的数据预取到快设备；但在**写密集**负载（SYSTOR17）上更差，因为它启发式的放置把所有数据放进快设备、触发频繁迁移。这说明：自适应的迁移策略需要**同样自适应**的放置策略才能持续获益。
5. **SAPM 平均比 Sibyl 差 21.9%（30.5%）**，原因：(1) 放置与迁移目标、时间尺度不同，单智能体无法同时有效优化；(2) SAPM 只在没有放置请求时才迁移，导致迁移不及时。

这些结果说明：现有技术以及本文为"单 RL 智能体"路线新开发的技术，都只孤立优化放置或迁移，而**朴素组合仍然不够**。

## 4 Harmonia

Harmonia 是一种面向 HSS 数据管理的在线 MARL 技术，含两个自治 RL 智能体（数据放置、数据迁移），实现在宿主 OS 的 HSS 管理层中。

### 4.1 关键设计挑战

1. **两项任务不同但相互依赖。** 激进的放置会触发不必要的迁移；延迟的迁移会限制放置的效果。缺乏协调时，独立学习的智能体可能**竞争而非合作**，造成不必要的数据移动与不稳定行为。
2. **环境非平稳。** 访问模式与设备状态持续演化；多智能体加剧非平稳性——每个智能体的决策都会改变另一个智能体观测到的环境，使收敛困难。
3. **多智能体增加计算与存储开销。** 由于放置在关键路径上，设计必须最小化推理延迟与内存占用。

论文指出：已有 MARL 工作使用 (1) 目标相同的同构智能体，和/或 (2) 联合动作空间与共享奖励——这些都不适用于 HSS，因为放置与迁移的目标、约束与时间尺度不同。

### 4.2 Harmonia 的 RL 形式化

Harmonia 由两个自治智能体组成（图 5），通过观测状态特征、执行动作、接收奖励与 HSS（环境）交互。两个智能体的状态、动作与奖励都经过设计，以支持协调并最大化 HSS 性能。

**状态。** 两个智能体共享同一个状态表示，含**七个特征**，刻画当前 HSS 状态与负载特征：I/O 请求特征、当前设备状态、页的访问与迁移历史。为在最小化运行时开销（推理延迟与元数据存储）的同时保留有用信息，Harmonia (1) 用特征选择挑出少量高相关特征，(2) 按负载刻画把每个特征量化到少量桶（表 1）。时刻 $t$ 的状态为七维观测向量：

$$O_t = (req\_size_t,\ req\_type_t,\ acc\_intr_t,\ acc\_freq_t,\ fast\_cap_t,\ curr\_dev_t,\ migr\_intr_t) \tag{1}$$

**表 1　Harmonia RL 智能体使用的状态特征**

| 特征 | 描述 | 桶数 | 编码（位） |
|---|---|---|---|
| $req\_type$ | 请求类型（读/写） | 2 | 1 |
| $req\_size$ | 请求尺寸（以页计） | 8 | 3 |
| $acc\_intr$ | 请求页的访问间隔 | 64 | 8 |
| $acc\_freq$ | 请求页的访问频率 | 64 | 8 |
| $fast\_cap$ | 快存储设备的空闲空间 | 8 | 3 |
| $curr\_dev$ | 请求页当前所在设备 | 2 | 1 |
| $migr\_intr$ | 页的迁移间隔 | 64 | 8 |

各特征说明：

- **请求类型**：读或写，1 位。
- **请求尺寸**：当前 I/O 请求的大小（按 4 KiB 页数计），量化为 8 类（1 页 ≤4 KiB、2 页 4–8 KiB、4 页 8–16 KiB、8 页 16–32 KiB、16 页 32–64 KiB、32 页 64–128 KiB、64 页 128–256 KiB、≥128 页 ≥512 KiB），3 位。
- **访问间隔**：同一页两次访问之间的页访问次数，反映时间局部性，8 位。
- **访问频率**：某页被访问的总次数，8 位。
- **快设备容量**：快设备剩余空闲空间，支持容量感知的放置与迁移决策，量化 8 桶，3 位。
- **当前设备**：页当前所在设备，提示迁移机会；取决于设备数，双设备 HSS 用 1 位。
- **迁移间隔**：同一页两次迁移之间的迁移次数，反映迁移稳定性，8 位。

整体状态表示用 **32 位**编码，从而支持快速特征查找与低延迟推理。对 $acc\_intr$、$acc\_freq$、$migr\_intr$ 等特征分配更高精度，以保证表示准确并可扩展到新负载与配置。Harmonia 在宿主 DRAM 中维护元数据表来跟踪状态特征；为平衡性能与容量，只在 DRAM 中保留**频繁访问的子集（宿主 DRAM 容量的 0.1%）**，其余元数据刷到快存储设备；两个智能体都通过查表观测当前状态。

**动作。** 两个智能体独立运作，动作空间取决于设备数。放置智能体为每个从应用发往 HSS 的**写**请求选择目标设备——放置决策只作用于写请求，因为读请求的目标设备由数据当前位置决定。迁移智能体为已放置的页选择迁移目标设备。双设备 HSS 中，智能体在快、慢设备之间选择。动作用 4 位编码以降低复杂度并支持扩展到更多设备。

**奖励。** 奖励结构是 RL 找到最优策略的关键。设计依据两点：以 I/O 延迟作为两个智能体的主要反馈信号（因为它综合反映了存储设备的内部状态——排队延迟、缓冲依赖、共享资源争用、垃圾回收、读写不对称、非阻塞操作、错误处理——因而是系统性能的稳健代理）；其次，通过奖励结构实现两智能体的协调。

- **放置智能体**的目标是改善当前 I/O 请求的延迟。每次放置动作在 $t+1$ 收到一个与 I/O 请求延迟成反比的**即时奖励**：

$$R_{placement} = \frac{1}{L_t} \tag{2}$$

其中 $L_t$ 是时刻 $t$ 的 I/O 请求延迟。尽管把数据放在快设备能获得更低延迟与更高奖励，Harmonia **并不贪婪地**总是这么做，而是学习平衡设备利用率，因为：(1) 快设备容量有限，过度使用会因排队延迟、带宽争用与垃圾回收反而降低性能；(2) 有选择地把不太关键的数据放到慢设备，可为延迟敏感请求保留快设备容量并减少争用。

- **迁移智能体**的目标是最大化**长期** HSS 性能，因为 (1) 应用可能不会立即访问被预取的数据，(2) 释放快设备容量带来的收益通常只在后续放置中体现。因此，在把 $x$ 个页迁移到各自目标设备后，迁移智能体收到一个**延迟奖励**，与随后 $n$ 个 I/O 请求的平均放置延迟成反比：

$$R_{migration} = \begin{cases} \dfrac{\sum_{i=t}^{t+n} P_{migr}}{\sum_{i=t}^{t+n} L_i} & \text{迁移 } x \text{ 个页之后} \\[4pt] 0 & \text{其他情况} \end{cases} \tag{3}$$

其中 $t$ 是当前时刻，$L_i$ 是第 $i$ 个 I/O 请求的延迟。为避免同一页的反复迁移（乒乓迁移），加入一个小的惩罚 $P_{migr}$，与 $x$ 个页的平均迁移间隔和访问间隔成反比（见表 1）。基于经验分析（§6.1），$n$ 取 50、$x$ 取 10（即迁移队列长度）。两个智能体的奖励都用 16 位表示以降低存储开销。

### 4.3 两个智能体之间的协调

协调通过两条途径实现：(1) 奖励，(2) 动作对共享 HSS 的影响。

- 放置智能体的奖励（式 2）鼓励有效利用快设备，而这依赖迁移智能体主动把冷（热）数据迁到慢（快）设备；
- 迁移智能体收到基于"迁移候选页之后 $n$ 个 I/O 请求放置延迟"的延迟奖励（式 3），这种延迟反馈鼓励能改善**未来**放置效果的迁移决策。

**缓解冲突。** 两种做法：

1. 迁移智能体监控访问间隔与迁移间隔都较大的页（表 1），并**忽略最近刚放置或刚迁移过的页**（例如上一请求中被访问过的页）；
2. 在迁移奖励中引入小惩罚（式 3），抑制同一页的反复迁移（乒乓迁移）。

**协调的效果。** 比较 Sibyl、**Harmonia（无协调）**、**Harmonia（有协调）** 的平均请求延迟（图 6）。两个关键观察：

1. Harmonia 在性能优先（成本优先）HSS 上平均优于无协调变体 **26.7%（59.8%）**，因为无协调的智能体会做出冲突决策；
2. 无协调变体在读密集负载上表现很差，因为迁移智能体不会把频繁读的页预取到快设备。

### 4.4 Harmonia 的设计

图 7 给出关键组件。

**数据放置智能体 ①。** 为每个到来的 I/O 写请求 ② 选择最合适的设备，依据 I/O 特征与 HSS 状态。含两个线程：(1) **放置训练线程 ③**，后台训练并更新放置策略；(2) **放置推理线程 ④**，Harmonia 唯一处在 I/O 关键路径上、做放置决策的线程。这种分离保证放置决策低延迟，同时允许持续在线学习。

**数据迁移智能体 ⑤。** 动态重组已放置的页：基于访问模式与 HSS 状态识别待迁页与其目标设备。为避免干扰放置，用两个后台线程实现：(1) **迁移训练线程 ⑥**，训练并持续更新迁移策略；(2) **迁移推理线程 ⑦**，持续监控已放置页、确定迁移候选与目标设备、把候选元数据推入**迁移队列 ⑧**。若某页的当前设备与目标设备相同，则不作为候选。这种完全异步的设计使数据重组可以主动进行，同时不增加关键路径上的放置延迟。

**迁移队列 ⑧。** 存放被选为迁移的页的元数据：逻辑页地址与目标设备标识（如 0 表示慢设备）。基于经验分析（§6.1），队列长度设为 **10**，以保证迁移及时。

**迁移线程 ⑨。** 专用后台进程，持续监控迁移队列并迁移页。为避免干扰放置并及时迁移，Harmonia 用实时监控工具（如 `iostat`）以较高频率采样设备带宽以**检测设备空闲期**并调度迁移。对高强度负载（YCSB、Baleen），该线程优先处理"已在迁移队列中、且与到来的读请求相关联"的页，并以低优先级写（low-priority write）方式发起迁移。

### 4.5 RL 智能体的设计

图 8 给出单个智能体的设计。每个智能体用**两个线程**——训练线程与推理线程——以同时实现持续学习与关键路径上的低延迟推理。

**推理线程。** (1) 从 I/O 请求与 HSS 观测输入特征（状态）ⓐ；(2) 用推理网络 ⓑ 做推理；(3) 选择使长期回报最大的动作 ⓒ；(4) 把状态、动作与奖励 ⓔ 作为经验 ⓕ 收集到经验缓冲区 ⓖ。

**训练线程。** 后台线程，周期性从经验缓冲区采样经验 ⓗ 以更新训练网络 ⓘ、优化放置或迁移策略。

**经验缓冲区。** 每个智能体维护独立缓冲区以反映其不同目标与时间尺度；使用经验回放，从缓冲区采样一批经验训练。缓冲区驻留宿主 DRAM，存最近 **1000** 条经验（基于经验分析）；更大的缓冲区能捕获更多访问模式，但增加存储开销。

**训练网络与推理网络。** 每个智能体使用相同的简单前馈网络：输入层 7 个神经元（每个状态特征一个）、一个 10 神经元的隐藏层、输出层 $N$ 个神经元（$N$ 为 HSS 设备数，双设备时 $N=2$）。隐藏层用 **swish** 激活；选择 Q 值最高的动作。**训练与推理网络分离**，以把训练延迟从 I/O 请求处理中移除；训练网络权重每 $K$ 个请求复制到推理网络，$K=1000$（基于经验分析，在策略及时更新与同步开销之间取得平衡）。

**RL 算法。** 使用 **C51** [253]，即分类式深度 Q 网络，更新每个智能体的 $Q(S,A)$。C51 学习每个状态-动作对 Q 值的**分布**，从而提供更丰富的反馈与更稳定的学习。

**超参数调优。** 通过交叉验证做一次性离线超参调优，取值见表 2。

**表 2　Harmonia RL 智能体的超参数**

| 超参数 | 取值范围 | 放置智能体 | 迁移智能体 |
|---|---|---|---|
| 折扣因子 $\gamma$ | 0–1 | 0.9 | 0.1 |
| 学习率 $\alpha$ | $1e^{-5}$–$1e^{0}$ | $1e^{-3}$ | $1e^{-2}$ |
| 探索率 $\epsilon$ | 0–1 | 0.001 | 0.001 |
| 批大小 | 64–256 | 128 | 256 |
| 经验缓冲区大小 | 10–10000 | 1000 | 1000 |

**探索与利用。** 每个智能体从零先验开始，随机做初始决策（探索），并利用经验逐步做出最优决策（利用）。采用 $\epsilon$-greedy：以 $1-\epsilon$ 概率选预测最优动作，以 $\epsilon$ 概率随机。

**收敛与适应性。** 为评估对访问模式变化的适应能力，设计一个在 **LUN0（写密集）与 ResNet50（读密集）之间每 5000 请求切换**的基准（图 9 展示两者的虚拟地址与请求尺寸变化，以及 Harmonia 在性能优先 HSS 上前 20000 请求的训练损失收敛）。三个关键观察：

1. 两个智能体的策略都在**前 5000 个请求内收敛**（训练损失接近零，Phase 1：LUN0）；
2. 当负载从 LUN0 切到 ResNet50（Phase 2）时，训练损失仍接近零，说明已学策略**能泛化到负载变化**；
3. 每次相位切换时出现小的瞬时尖峰（见插图），但训练损失仍然很低，策略在**数百个请求内**重新收敛，显示出快速适应性。

**回退机制。** 为避免每个智能体探索阶段的随机初始决策，Harmonia 支持回退到基线系统行为：可在运行时禁用 Harmonia，把放置与迁移决策还原为 OS 默认策略。这允许管理员 (1) 仅在每个智能体学到稳定策略后启用 Harmonia，或 (2) 对访问模式可预测的负载（如元数据密集的顺序负载）禁用 Harmonia。

### 4.6 开销分析

#### 4.6.1 存储开销

五个组成部分：

1. **神经网络**：每个智能体使用 7–10–2 前馈网络、16 位浮点权重。四个网络（两智能体各自的训练 + 推理）各 90 个权重（$7\times10+10\times2$），合计 **6 KiB**（约 1.5 KiB × 4），可完全放入 CPU 缓存。
2. **经验缓冲区**：两个缓冲区（每智能体一个）各存 1000 条经验、各需 100 KiB，合计 **200 KiB**。
3. **迁移队列**：存 10 个候选的逻辑块地址（32 位）+ 目标设备 ID（4 位），需 **50 B**。
4. **迁移奖励**：临时保存 50 个 I/O 延迟（$n$ 由经验分析确定），约 **100 B**。
5. **元数据表**：存状态特征，每条 32 位（表 1），相当于 4 KiB 页的 0.1%。

#### 4.6.2 延迟开销

低延迟来自三方面：(1) 轻量 RL 智能体；(2) 训练与推理分离；(3) 非关键线程（如迁移推理线程）后台执行。训练与推理在宿主 CPU 上执行，因为网络轻量、权重可放入 L1 数据缓存。

**推理延迟。** 每次推理需 **90 次 MAC**（$7\times10+10\times2$）。在评估系统（表 3）上，每次推理约 **90 个 CPU 周期（240 ns）**，低于高端 SSD 的 I/O 读延迟（约 3 µs）。只有**放置**智能体的推理计入 I/O 延迟，因为它处在关键路径上；迁移智能体在后台推理，其延迟不直接影响进行中的 I/O 请求的放置。

**训练延迟。** 训练在后台执行，不直接影响 I/O 请求。每个训练步处理 16 个批次，每批 128 个样本，共 **184,320 次 MAC**（$16\times(128\times7\times10+128\times10\times2)$）。在评估的八核 CPU 上，每个训练步约 **200,000 周期（约 53 µs）**。

**元数据采集延迟。** Harmonia 的自定义 Linux 块设备驱动拦截 I/O 请求、提取状态特征并更新元数据表。用内核级时间戳测得：每个 I/O 请求 (1) 元数据采集约 **100 ns**，(2) DRAM 中的元数据表更新耗时 **1 µs**。

各类负载的选取理由：

- **SYSTOR17**：企业虚拟桌面基础设施（VDI）的存储流量；
- **RocksDB**：键值存储，影响写放大与空间局部性；
- **YCSB**：云数据库操作（插入、更新、读、扫描）；
- **MLPerf Storage**：现代 ML 与数据分析流水线（图像分类、参数预测）；
- **LLM**：三个负载覆盖训练与推理的主要 I/O 行为——**LLM-Checkpoint** 覆盖 7B 参数 LLM（如 LLaMA-2-7B）训练时的周期性检查点写入与恢复读，产生突发顺序写 + 读主导的恢复阶段；**LLM-Weights** 覆盖 7B 参数模型（如 OPT-6.7B）的重复权重加载，压测冷启动延迟、大顺序读与页缓存交互；**LLM-KVCache** 记录细粒度的 KV-cache 换出与重载行为，产生小而延迟敏感的读写，且局部性快速漂移；
- **Baleen**：Meta 生产环境的 ML 数据流水线与模型服务 I/O 行为；**不用于超参调优**，作为**未见负载**评估适应性。

**多程序负载（表 5）。** 通过并发运行多个负载构造六个多程序负载，依据三个因素：(1) 读密集、写密集、混合负载的组合，(2) 达到高 I/O 强度所需的并发数，(3) 不同请求尺寸。每个组成负载运行在单独线程上（如 mix6 有八个并发线程）。

**指标。** 四个关键指标：

1. **平均 I/O 请求延迟**：完成一次应用 I/O 请求所需的平均时间；
2. **端到端吞吐**（IOPS）：HSS 的整体请求处理速率；
3. **尾延迟**：I/O 请求延迟的第 99 与第 99.99 百分位；
4. **写放大（WA）**：写入所有 HSS 设备的总数据（含迁移引起的写）与工作负载自身写数据之比。WA = 1 表示除应用写之外没有额外写；WA 越高，设备寿命受损越大。

## 6 评估

### 6.1 性能分析

**I/O 请求延迟与端到端吞吐。** 图 11(a)(b) 给出性能优先与成本优先 HSS 上各技术的平均 I/O 请求延迟（归一化到 Fast-Only），图 12(a)(b) 给出端到端吞吐。四个关键观察：

1. **Harmonia 在两种配置上都持续优于所有基线。** 在性能优先（成本优先）HSS 上，相对最佳先前方案 Sibyl，延迟改善 **29.3%（44.8%）**，端到端吞吐提升 **49.4%（136.7%）**。这些收益证明了同时优化放置与迁移的价值。
2. **Harmonia 的性能接近 Oracle。** 平均延迟比 Oracle 高 **41.0%（33.1%）**，吞吐达到 Oracle 的 **75.5%（69.2%）**。这说明其协同在线学习策略在没有未来访问模式知识的情况下也能做出有效决策。
3. **Harmonia 在读密集负载（RocksDB、MLPerf）上的改善大于写密集负载（SYSTOR17）。** 平均而言，在性能优先（成本优先）HSS 上，读密集负载优于 Sibyl **57.5%（43.2%）**，写密集负载优于 **41.0%（39.9%）**。读密集场景下，Harmonia 即使没有应用写，也会主动把频繁访问的页预取到快设备，降低读延迟并提升吞吐；写密集场景下，它主动把冷页迁出快设备以容纳新的到来写。在 MLPerf 与 LLM 负载中，Harmonia 学会把频繁复用的训练数据留在快设备、把冷数据后台迁走，相比先前方案降低了快存储争用。
4. **改善在成本优先 HSS 上更大**，原因：(1) 成本优先 HSS 上两设备延迟差距大，迁移开销本身更大；(2) 多个基线在 I/O 关键路径上做迁移，引入显著延迟；(3) Harmonia 在系统空闲期主动迁出冷页，在不干扰到来 I/O 请求的情况下腾出快设备空间。

**尾延迟。** 图 13(a)(b) 给出性能优先 HSS 上三个代表性负载（LUN0 写密集、ssd-00 读密集、YCSB-B 混合）的第 99、99.99 百分位延迟。两个观察：

1. Harmonia 显著降低尾延迟：平均比 Sibyl 低 **32.3%（99 分位）/ 25.3%（99.99 分位）**。收益来自在低利用率期间执行迁移，避免干扰关键路径上的延迟敏感 I/O。
2. K-SVM、RNN-HSS、Sibyl+K-SVM、Sibyl+RNN-HSS 的尾延迟非常高，因为它们在**固定间隔**做批量迁移，引入设备争用与排队延迟。

**迁移队列大小的敏感性（图 14(a)）。** 三个观察：队列大小为 **10** 时延迟最低；小队列（<5）限制候选数量，丢弃许多有用候选导致性能下降，队列为 0 时不做迁移、性能很差；大队列存更多候选，但更可能包含过期条目，使迁移决策不再反映当前系统状态。

**迁移智能体奖励中 $n$ 的敏感性（图 14(b)）。** $n$ 决定迁移智能体评估其决策影响的时间跨度，最优值取决于 (1) 迁移后到来 I/O 请求的间隔，(2) 负载访问模式（访问频率、复用距离），(3) 系统条件（设备容量）。三个观察：

1. 本配置最优 $n=50$；
2. 小的 $n$（<10）无法体现迁移收益，因为迁移的影响只有在足够多未来 I/O 请求发生后才显现——(i) 迁移释放快设备空间后，要等到后续大量放置用到这些空间才见延迟改善；(ii) 迁移预取页后，要等这些页被多次访问才见收益；
3. 大的 $n$（如 250）会稀释迁移奖励的影响，因为其中许多未来 I/O 请求可能与已迁移的页无关，或到来得太晚、无法受益于释放的快设备空间。

**带持久内存（PMEM）的 HSS（图 15）。** 为展示对新存储技术的可扩展性，在 PMEM + 高端 SSD 的 HSS 上评估。由于这类设备尚不普及，用 **RAMDisk 模拟 PMEM** 的延迟特性。三个观察：

1. 平均而言，Harmonia 优于最佳基线 Sibyl **19.4%**；比 Oracle 高 **28.0%** 的延迟；这些收益来自放置与迁移的联合优化；
2. CDE 与 CDE+RL-Migr 把所有数据放进 PMEM、利用其低写延迟，但 PMEM 因每比特成本高、密度低而容量远小于 SSD，容量受限导致频繁迁移、消耗带宽并干扰进行中的 I/O，从而削弱"激进放置到 PMEM"的收益；
3. Harmonia 在读密集负载（RocksDB、MLPerf）上改善更大，因为它主动把数据预取到 PMEM，使更多读落在 PMEM 上。

**多程序负载（图 16）。** 两个观察：

1. Harmonia 在所有负载与配置上都优于先前方案：在性能优先（成本优先）HSS 上优于 Sibyl **32.8%（25.3%）**，比 Oracle 高 **35.4%（54.7%）** 的延迟；
2. **并发越高，Harmonia 的改善越大**：在八个并发负载（mix6）上对 Sibyl 的改善最大，为 **39.4%（41.8%）**。并发增加使访问模式更动态、应用间干扰更强，Harmonia 的 RL 策略比先前方案适应更快。

**未见负载（图 17）。** 在五个未参与超参调优的 Meta 生产负载上评估：Harmonia 在性能优先（成本优先）HSS 上平均优于 Sibyl **31.2%（31.5%）**。这证明多智能体 RL 框架能**泛化**到调优之外的工作负载；虽然超参是针对这些负载调过的，但其在线学习式的放置与迁移策略能适应变化的访问模式，而 Sibyl 依赖的启发式迁移策略适应能力有限。

### 6.2 扩展到 HSS 中的多设备

对比 Harmonia 与 Sibyl 在三设备与四设备 HSS 上的表现（其他基线因设计与固定配置绑定、缺乏可扩展性而未评估）。两个观察：

1. Harmonia 在两种配置上都持续优于 Sibyl：三设备（四设备）平均延迟改善 **38.9%（39.2%）**。收益来自把性能关键数据放在高端与中端设备、并在空闲期把冷数据迁到低端设备；相比之下 Sibyl 经常在关键路径上把数据驱逐到低端设备，引入显著延迟开销；
2. 在读密集负载（RocksDB、MLPerf）上改善更大（最高 **58.3%**），因为 Sibyl 主要依赖应用写来迁移数据。

### 6.3 对设备寿命的影响

用写放大（WA）评估对存储设备寿命的影响（图 19）。两个观察：

1. **只有 Sibyl 与 RNN-HSS 的 WA 比 Harmonia 低。** 在性能优先（成本优先）HSS 上，Harmonia 平均 WA 为 **1.44（1.54）**，Sibyl 为 1.38（1.50），RNN-HSS 为 1.09（1.07）。Harmonia 更高的 WA 来自读密集负载中为提升读性能而主动预取数据到快设备。
2. Harmonia 的 WA 在不同负载类型间差异显著：写密集负载（SYSTOR17）下 WA 更低（1.24），读密集负载（RocksDB、MLPerf）下更高（1.80），因为写密集场景中 Harmonia 会**顺带**在应用触发的更新中迁移数据，减少额外迁移流量。

结论：**Harmonia 以略增写放大换取显著的延迟改善。**

**Harmonia 的写流量分布（图 20）。** 两个观察：(1) Harmonia 把更多数据迁往慢设备，以为频繁访问的数据保留快设备容量；(2) 在读密集负载（RocksDB、MLPerf）中，即使没有应用更新，它也会把频繁读的数据主动预取到快设备，因此对快设备的写更多。

## 7 讨论

**替代目标与奖励结构。** Harmonia 目前用基于 I/O 延迟的奖励来提升性能，但其 RL 形式化可适配其他目标，如设备寿命、公平性、服务质量（QoS）与能效。例如寿命优化可把写次数、设备耐久上限、写放大、设备可靠性特征（NAND 类型、ECC）加入状态与奖励；公平性与 QoS 可纳入带宽、队列深度、应用需求等指标。这些扩展只需改变状态表示与奖励形式，**无需修改 Harmonia 架构**。

**可扩展性。** 扩展到四设备以上只需极小改动。每增加一个存储设备，需要对每个智能体的训练与推理网络做两处修改（见 §4.5）：(1) 增加一个输入节点（表示新设备的容量利用率，见表 1），(2) 增加一个输出节点（表示新的放置或迁移动作）。每个新增设备带来 **8 个额外节点**（2 智能体 × 2 网络 × 2 节点），合计增加 **1.3 KiB** 存储开销与约 **40 ns** 的推理/训练延迟——相对于存储设备访问延迟可忽略。每个新增设备使每条元数据表项增加 3 位以记录该设备的容量利用率。

**对其他系统的适用性。** Harmonia 的设计适用于分层内存/存储、混合内存、解耦内存/存储等系统：

- 在**分层内存/存储**中，放置策略通常是静态的（默认放到最上层最快的设备），迁移策略在相邻层间移动数据；
- 在**混合内存**中，可调整 Harmonia 的 RL 形式化以适应更严格的延迟约束（更轻量的状态表示、表格式 RL）；
- 在 **CXL 解耦内存/存储**中，可把 Harmonia 部署在 CXL fabric 控制器中，协调跨池化资源的放置与迁移决策。

## 8 相关工作

据作者所知，Harmonia 是**第一个**在混合存储系统中联合优化数据放置与数据迁移的多智能体 RL 全流程数据管理技术。论文已在定性与定量上与最先进的放置（[86, 102]）与迁移（[103, 106]）技术比较。

**HSS 数据管理。** 大量先前工作提出启发式与 ML 式的放置与迁移技术。`mdadm`、LVM 等内核工具支持软件 RAID 与虚拟分区，但把放置与迁移留给应用或管理员；Harmonia 提供自适应的、应用透明的放置与迁移。迁移方面，Vengerov 在分层存储中使用模糊规则；ArtMem 提出面向分层内存的 RL 页迁移——但二者都未**联合**优化放置与迁移，且都依赖**表格式** RL（显式维护状态-动作表），可扩展性受限于设备数与特征数增长。

**存储系统中的 RL。** 多项先前工作把 RL 用于存储系统，聚焦云利用率、SSD 吞吐与 QoS 优化、垃圾回收与错误缓解等维护任务。Harmonia 与这些工作**正交**，可与其集成。

**面向体系结构优化的 RL。** RL 也广泛用于数据预取、内存调度、缓存替换、片上网络仲裁等。这些工作表明 RL 能在复杂的硬件管理环境中有效学习控制策略；Harmonia 把这一思路扩展至 HSS 的跨设备数据管理。

**多智能体 RL 系统。** 多项先前工作用 MARL 做系统优化：无服务器计算平台的延迟优化、CPU 缓存管理策略、SMR 盘的缓存清理等。这些工作使用**同构智能体**（相同目标、共享动作空间与奖励函数），因为每个智能体解决的是相似子问题、时间尺度相同。而 HSS 的放置与迁移目标与时间尺度不同，因此 Harmonia 使用**异构智能体**（不同的动作与奖励结构）。

与 **RLRP** 的对比：RLRP 面向分布式存储的副本放置与迁移，但 (1) 只在粗粒度时间间隔动作（如仅在拓扑变化时），(2) 仅在拓扑变化时重训，(3) 只用设备相关状态特征。Harmonia 则在 HSS 中做**细粒度**的页级放置与迁移，并持续在线更新策略以适应快速变化的负载；它表明当不同任务处于不同时间尺度与目标时，异构智能体的 MARL 形式化是有益的，补充了以"同构智能体复制到相似资源"为主的先期 MARL 系统。

---

## 9 结论

我们提出 **Harmonia**，第一个基于多智能体 RL 的 HSS 全流程数据管理技术，联合优化数据放置与数据迁移。Harmonia 用两个协同的 RL 智能体，共享状态表示，但在不同时间尺度上优化互补的目标：放置智能体在关键路径上为 I/O 请求数据选择最合适的设备；迁移智能体在低利用率期间主动重组已放置的数据，以改善长期系统性能。通过协调的奖励结构与轻量状态表示，Harmonia 以低延迟与低存储开销实现两智能体的有效协作。

真实系统评估表明，Harmonia 在四种 HSS 配置、广泛负载上显著优于八种先前与新的 HSS 数据管理技术，并且易于扩展到不同 HSS 配置。其性能收益伴随低延迟与低存储开销。
